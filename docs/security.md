# Cloud Bookmark security model

## No-login library access

Cloud Bookmark does not require an application account for normal bookmark use.

Each library uses a secret bearer token:

- New tokens are generated by the Worker with 256 bits of cryptographic randomness.
- Token format: `v1.<random>.<HMAC-SHA256 signature>`.
- The HMAC signing key exists only as the Cloudflare secret `TOKEN_SIGNING_SECRET`.
- D1 never stores the plaintext token. The library namespace is derived with SHA-256 from the token payload plus the `book` name.
- The browser stores the active token in localStorage.
- Share/device-transfer links put the token in the URL fragment (`#token=...`) rather than the query string. The fragment is removed from the address bar after import.

## Abuse protection

Worker Rate Limiting bindings are configured in `wrangler.jsonc`:

- `TOKEN_ISSUE_LIMIT`: 12 new tokens / minute / source.
- `INVALID_TOKEN_LIMIT`: 30 invalid-token attempts / minute / source.
- `LEGACY_TOKEN_LIMIT`: 12 legacy-token requests / minute / source.
- `VALID_TOKEN_LIMIT`: 300 API requests / minute / library scope.

Invalid signed tokens are rejected before any D1 query.

Cloudflare Worker rate limits are approximate and local to a Cloudflare location. They are an abuse-control layer, not a strict accounting mechanism.

## Legacy-token migration

The earlier prototype generated 40-character hexadecimal tokens in the browser.

Those tokens remain temporarily accepted through the stricter legacy rate-limit path so existing D1 data is not lost. When an existing legacy library is successfully read or written and `TOKEN_SIGNING_SECRET` is configured, the Worker returns a signed replacement token in `x-library-token-upgrade`. The frontend stores that replacement automatically.

Because the signed token wraps the original legacy token as its payload, the derived D1 namespace remains unchanged.

## Required Cloudflare secret

Do not commit the signing secret to Git or Wrangler config.

Generate the secret once, then put the exact same value into both Production and Preview Base while they share the same D1 database:

```sh
SECRET="$(openssl rand -hex 32)"
printf '%s' "$SECRET" | npx wrangler secret put TOKEN_SIGNING_SECRET
printf '%s' "$SECRET" | npx wrangler preview base-config secret put TOKEN_SIGNING_SECRET
```

Do not run the random generator separately for Production and Preview; existing signed tokens must verify in both environments if both point at the same library data.

In the Cloudflare dashboard the equivalent setting is under the Worker's **Settings → Variables and secrets**. Configure both **Production** and **Previews Base**.

## Token-loss behavior

The token is the library key. The browser remembers it locally, but clearing site storage removes that remembered key.

Use **Copy library secret link** before moving to another browser/device. Anyone who receives that secret link can access that library, so treat it like a password.
